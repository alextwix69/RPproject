# Roadmap 25.05: effective_user, users storage и main menu callbacks

Дата: 2026-05-25

## Цель

Подготовить основу для будущей регистрации users в online-rp-lobby:

- сохранять всех Telegram-пользователей, которые взаимодействуют с ботом;
- обновлять данные из `update.effective_user`;
- сделать главное меню на inline-кнопках;
- централизованно обрабатывать callbacks из main menu;
- подготовить кнопку регистрации как точку входа в будущий registration flow.

В этом рабочем блоке не делаем полноценную регистрацию, каталог, платежи, бронирование и админские сценарии.

## Общее решение

### Хранение пользователей

Создаем/используем модель `User`, которая хранит всех Telegram-пользователей, а не только тех, кто завершил регистрацию.

Минимальные поля:

- `id`: внутренний primary key.
- `telegram_id`: `effective_user.id`, unique, обязательное поле.
- `username`: `effective_user.username`.
- `first_name`: `effective_user.first_name`.
- `last_name`: `effective_user.last_name`.
- `language_code`: `effective_user.language_code`.
- `is_bot`: `effective_user.is_bot`.
- `role`: например `user`, `admin`.
- `is_registered`: флаг завершенной lobby-регистрации, по умолчанию `False`.
- `first_seen_at`: первое взаимодействие с ботом.
- `last_seen_at`: последнее взаимодействие с ботом.
- `created_at`, `updated_at`: технические timestamps.

Ключевая идея: `telegram_id` отвечает за факт существования Telegram-пользователя в базе, а `is_registered` отвечает только за прохождение будущей регистрации в online-rp-lobby.

### Обработка effective_user

Единая сервисная функция:

```python
ensure_user_from_effective_user(effective_user) -> User | None
```

Логика:

- если `effective_user is None`, вернуть `None` или контролируемо обработать ситуацию;
- найти пользователя по `telegram_id`;
- если пользователя нет, создать запись;
- если пользователь есть, обновить Telegram-поля и `last_seen_at`;
- не сбрасывать `is_registered` при обычном обновлении Telegram-данных.

Вызывать минимум в `/start` и в callback handler главного меню.

### Main menu

Главное меню делаем через `InlineKeyboardMarkup`.

Структура:

```text
[ Зарегистрироваться ]
[ Профиль ] [ Лобби ]
[ Помощь ]
```

Callback-data:

- `main:register`
- `main:profile`
- `main:lobby`
- `main:help`

Кнопка `Зарегистрироваться` стоит первой отдельной строкой, потому что это главный вход в следующий этап проекта.

## Распределение ролей

### alextwix: users storage и effective_user

Зона ответственности: модель пользователя, repository/service contract, сохранение и обновление данных из Telegram user.

Основные файлы:

- `src/models/user.py`
- `src/models/base.py`
- `src/repositories/user_repo.py`
- `src/services/user_service.py`
- тесты user service/repository

Задачи:

- Описать `User` model с unique `telegram_id`.
- Добавить repository-методы:
  - `get_by_telegram_id`;
  - `create_from_effective_user`;
  - `update_from_effective_user`;
  - `ensure_from_effective_user`.
- Добавить сервисную функцию `ensure_user_from_effective_user`.
- Сделать mapper из `effective_user` в поля модели.
- Обработать `effective_user is None`.
- Гарантировать, что повторный `/start` или callback не создает дубль.
- Гарантировать, что `is_registered` не сбрасывается при обновлении Telegram-профиля.

Результат alextwix: любой пользователь, который взаимодействует с ботом, сохраняется и обновляется через один понятный сервисный вход.

### laurencic: inline keyboard и Telegram callback handler

Зона ответственности: визуальная структура главного меню, сборка inline keyboard, подключение Telegram handlers.

Основные файлы:

- `src/keyboards/inline_buttons.py`
- `src/keyboards/kb_build.py`
- `src/handlers/start.py`
- будущий handler/callback module для main menu
- `src/bot.py`, если нужно подключить handler регистрации callbacks

Задачи:

- Пересобрать главное меню как `InlineKeyboardMarkup`.
- Заменить временные `Кнопка 1`, `Кнопка 2` на реальные пункты:
  - `Зарегистрироваться`;
  - `Профиль`;
  - `Лобби`;
  - `Помощь`.
- Использовать согласованные callback-data:
  - `main:register`;
  - `main:profile`;
  - `main:lobby`;
  - `main:help`.
- Обновить `/start`, чтобы он показывал новое inline-menu.
- Добавить `CallbackQueryHandler` с pattern `r"^main:"`.
- В callback handler:
  - вызвать `query.answer()`;
  - вызвать сервис сохранения/обновления пользователя;
  - передать `query.data` в router;
  - выбрать ответ по intent.

Результат laurencic: пользователь видит рабочее inline main menu, а нажатия кнопок доходят до централизованной обработки.

### дезидоупкинс: callback contract, router, UX-тексты и тесты

Зона ответственности: независимая от Telegram/БД маршрутизация callback-data, тексты ответов и тесты контракта. Эта работа идет параллельно, не дожидаясь готовой БД или готовых кнопок.

Основные файлы:

- отдельный модуль для router, например `src/callbacks/main_menu.py`;
- тесты callback routing;
- при необходимости модуль с текстами ответов.

Задачи:

- Зафиксировать соответствие `callback_data -> intent`:
  - `main:register` -> `REGISTER`;
  - `main:profile` -> `PROFILE`;
  - `main:lobby` -> `LOBBY`;
  - `main:help` -> `HELP`;
  - неизвестный `main:*` -> `UNKNOWN`.
- Реализовать чистую функцию:

```python
resolve_main_menu_callback(callback_data: str) -> MainMenuIntent
```

- Функция не должна обращаться к Telegram `Update`, БД или registration logic.
- Подготовить UX-тексты:
  - `/start`;
  - ответ для `REGISTER`;
  - ответ для `PROFILE`;
  - ответ для `LOBBY`;
  - ответ для `HELP`;
  - fallback для `UNKNOWN`.
- Написать тесты:
  - `main:register` возвращает `REGISTER`;
  - `main:profile` возвращает `PROFILE`;
  - `main:lobby` возвращает `LOBBY`;
  - `main:help` возвращает `HELP`;
  - неизвестный `main:*` возвращает `UNKNOWN`;
  - callback вне namespace `main:` не ломает router.

Результат дезидоупкинс: есть проверенный callback contract, к которому laurencic подключает реальный Telegram handler.

## Параллельный порядок работы

### Первые 15 минут: общий контракт

Все трое синхронизируются по:

- именам callback-data;
- названию intent enum/констант;
- месту хранения текстов;
- имени сервисной функции для `effective_user`.

После этого каждый работает в своей зоне.

### 15-90 минут: независимая реализация

- `alextwix`: модель, repository, service для `effective_user`.
- `laurencic`: keyboard builder, `/start`, skeleton callback handler.
- `дезидоупкинс`: router, intent contract, тексты, unit-тесты router.

### 90-140 минут: стыковка

- `laurencic` подключает router от `дезидоупкинс` в Telegram handler.
- `laurencic` подключает service от `alextwix` в `/start` и callback handler.
- `alextwix` проверяет, что handler не обходит user service.
- `дезидоупкинс` проверяет, что callback-data в keyboard совпадают с router-тестами.

### 140-180 минут: стабилизация

- Прогнать тесты.
- Исправить несовпадения imports/names.
- Убедиться, что `main:register` является готовой точкой входа для будущей регистрации.
- Зафиксировать TODO только для следующего этапа регистрации.

## Definition of Done

- Все Telegram-пользователи сохраняются по `effective_user.id`.
- Повторное взаимодействие обновляет Telegram-данные и `last_seen_at`.
- `is_registered` отделен от факта существования пользователя в базе.
- `/start` показывает inline main menu.
- Главное меню использует согласованные callback-data `main:*`.
- Callback routing покрыт тестами отдельно от Telegram.
- Telegram callback handler вызывает user service и router.
- `main:register` готов как entrypoint для будущего registration flow.

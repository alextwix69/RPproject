## 1. Что такое RoleHub

RoleHub - Telegram-бот для ролевого общения по фандомам. Пользователь выбирает вселенную и персонажа, создаёт собственный игровой мир или присоединяется к чужому лобби. Общение происходит в личном чате с ботом: бот сохраняет и пересылает сообщения другим участникам того же лобби.

Основная аудитория: дети и подростки 12-14 лет.

Основные продуктовые идеи:

- быстро погружать пользователя в любимый фандом;
- давать выбрать уникальную роль персонажа;
- объединять игроков в тематические RP-лобби;
- постепенно развивать профили, друзей, оформление и Premium;
- сохранять простой интерфейс на Telegram reply- и inline-кнопках.

Публичные контакты:

- бот: `@RoleHubBot`;
- канал: `@RoleHubChannel`;
- администратор поддержки: `@sanyasigma2006`.

## 2. Обязательная стилистика интерфейса

Весь пользовательский текст должен быть написан в **childish-majestic vibe**.

Требования:

- обращаться к пользователю как к герою или исследователю миров;
- использовать понятные образы миров, порталов, королевств, приключений, ролей и сокровищ;
- использовать уместные эмодзи: `✨`, `👑`, `🌌`, `🌟`, `🏰`, `💎`, `🎭`, `🔮`;
- сохранять короткие и однозначные подписи кнопок;
- писать понятно для аудитории 12-14 лет;
- не использовать сюсюканье и не перегружать строку эмодзи;
- ошибки тоже писать дружелюбно, но не скрывать их точный смысл;
- технические данные в админ-панели оставлять точными.

Пример:

```text
Плохо:  Пользователь не найден.
Хорошо: 🌙 Герой не найден. Проверь имя и попробуй ещё раз ✨
```

Текущие основные кнопки:

```text
🌌 Войти в мир
🤝 Друзья и герои
💎 Лавка сокровищ
⚙️ Настройки героя
🪄 Магическая поддержка
```

## 3. Технологии

- Python `>=3.12`;
- `python-telegram-bot >=21.0`;
- SQLAlchemy `>=2.0`;
- `python-dotenv`;
- SQLite в локальной конфигурации, но URL базы передаётся через окружение;
- pytest `>=8.0` для тестов;
- polling, не webhook, в текущей точке запуска.

Файл зависимостей: `pyproject.toml`.

## 4. Установка и запуск

Из корня репозитория:

```powershell
python -m pip install -e ".[test]"
python -m pytest
python -m src.bot
```

Точка входа: `src/bot.py`.

При запуске:

1. вызывается `create_db_tables()`;
2. создаются отсутствующие таблицы;
3. для старой SQLite БД добавляются некоторые отсутствующие nullable-колонки;
4. собирается Telegram `Application`;
5. регистрируются handlers;
6. запускается фоновая очистка истёкших лобби;
7. запускается polling.

В текущей рабочей среде PID обычно записывается в `logs/bot.pid`, но сам проект не содержит полноценного process manager. Для production нужен отдельный сервис, Docker entrypoint или supervisor.

## 5. Переменные окружения

Проект читает `.env` из корня репозитория.

Минимальная конфигурация:

```dotenv
API_KEY="telegram_bot_token"
DATABASE_URL="sqlite:///rolehub.db"
OWNER_IDS=123456789,987654321
```

Переменные:

- `API_KEY` - токен Telegram-бота;
- `DATABASE_URL` - SQLAlchemy URL базы данных;
- `OWNER_IDS` - Telegram ID владельцев через запятую;
- `ADMIN_IDS` - legacy-переменная, используется как fallback, только если `OWNER_IDS` отсутствует.

Правила безопасности:

- никогда не коммитить `.env`;
- никогда не выводить токен в ответах, логах или документации;
- владельцы из `OWNER_IDS` автоматически имеют и owner-, и admin-доступ;
- обычные админы дополнительно хранятся как `users.role = "admin"`.

## 6. Архитектура

Основной поток зависимостей:

```text
Telegram Update
  -> handler
  -> service
  -> repository
  -> SQLAlchemy model / database

handler
  -> render
  -> keyboard
  -> Telegram response
```

Ответственность слоёв:

- `handlers/` принимают Telegram updates и маршрутизируют сценарии;
- `services/` содержат бизнес-правила;
- `repositories/` выполняют запросы к БД;
- `models/` описывают таблицы SQLAlchemy;
- `render/` собирает пользовательские тексты экранов;
- `keyboards/` собирает reply- и inline-клавиатуры;
- `constants/` хранит темы, роли и pending-actions;
- `core/` отвечает за конфигурацию, БД и логирование;
- `utils/` содержит маленькие чистые функции.

Нельзя:

- писать SQL прямо в handler;
- отправлять Telegram-сообщения из repository;
- изменять ORM-состояние из render;
- размещать бизнес-правила в keyboard-файлах;
- дублировать текст кнопки строкой в разных местах, если уже есть константа.

## 8. Порядок регистрации handlers

В `build_application()` handlers подключаются так:

1. `track_incoming_message`, group `-1`;
2. `/start` и `/clear`;
3. admin handlers;
4. общий `main_menu` router;
5. lobby callbacks, `/leave` и общий lobby message handler.

Порядок важен. Узкие command/button handlers должны получить update раньше широкого lobby message handler.

## 9. Модель данных

### User

Основные поля:

- `id` - внутренний DB ID;
- `telegram_id` - уникальный Telegram ID;
- `username`, `first_name`, `last_name`, `language_code`;
- `display_name` - уникальное RoleHub-имя, 2-32 символа;
- `avatar_file_id` - Telegram `file_id` фотографии;
- `profile_data` - JSON для будущего расширения профиля;
- `role` - `user` или `admin`;
- `news_notifications_enabled`;
- `is_registered`;
- `current_lobby_id`;
- `pending_action`;
- `create_state` - JSON временного состояния;
- `first_seen_at`, `last_seen_at`, `created_at`, `updated_at`.

`ensure_from_effective_user()` создаёт пользователя или обновляет Telegram-поля и `last_seen_at`. Поле `is_registered` при обычном обновлении не сбрасывается.

### Friendship

- `requester_id`;
- `addressee_id`;
- `status`, сейчас используется `pending`;
- timestamps;
- уникальная направленная пара requester/addressee.

Repository ищет связь в обе стороны, поэтому повторную или обратную заявку создать нельзя.

### Lobby

- уникальный `code`;
- `topic`;
- `mode`, сейчас только `rp`;
- `owner_id`;
- `max_players`, `players_count`;
- `privacy`: `public` или `private`;
- `status`: `waiting`, `active`, `closed`;
- timestamps и `expires_at`.

### LobbyMember

- `lobby_id`, `user_id`;
- уникальная роль внутри RP-лобби;
- `is_owner`;
- `status`: `joined` или `left`;
- timestamps.

### LobbyMessage

Хранит сообщения активного лобби: тип, текст или `file_id`, отправителя, лобби и время.

Поддерживаемые типы Telegram-сообщений:

- текст;
- фото;
- стикер;
- voice.

## 10. Состояние пользователя

Временное состояние хранится в самой таблице `users`.

`pending_action` означает, что следующее сообщение пользователя нужно трактовать специальным образом.

Текущие значения:

```text
enter_lobby_code
search_create_role
create_max_players
search_join_role:<code>
set_display_name
set_profile_photo
find_friend
```

`create_state` хранит JSON. Часто используемые ключи:

- `reply_scene` - экран игрового сценария;
- `menu_scene` - экран общего меню;
- `topic`, `privacy`, `role`, `max_players`;
- `code`;
- `page`;
- `found_friend_id`.

При выходе в главное меню pending-action и временное состояние должны очищаться. Нельзя оставлять пользователя в ожидании текста или фото после смены раздела.

## 11. Доступ к dev-сборке

Текущая логика `/start`:

1. создать или обновить User;
2. если пользователь не owner и не admin, показать сообщение о разработке;
3. предложить перейти в `@RoleHubChannel`;
4. owner/admin продолжает в рабочую часть;
5. если у owner/admin нет `display_name`, запросить RoleHub-имя;
6. иначе открыть главное меню.

Важно: dev-проверка сейчас находится только внутри `/start`. Это не глобальный middleware. Теоретически обычный пользователь может вызвать другие handlers напрямую, например `/clear`, если знает команды. Если требуется настоящий закрытый доступ, нужно добавить общий access guard.

## 12. Главное меню и навигация

Главное меню:

```text
🌌 Войти в мир
🤝 Друзья и герои
💎 Лавка сокровищ
⚙️ Настройки героя
🪄 Магическая поддержка
```

Если пользователь уже состоит в незакрытом лобби, сверху появляется:

```text
↩️ Вернуться в свой мир
```

Навигация:

- `🏰 Главное меню` очищает временные состояния и возвращает в корень;
- `↩️ Назад` в общих разделах в конечном счёте ведёт в главное меню;
- внутри lobby-flow кнопка `Назад` возвращает на логический предыдущий шаг;
- старые подписи Telegram-кнопок поддерживаются через `LEGACY_BUTTON_ALIASES` и `LEGACY_LOBBY_BUTTON_ALIASES`;
- alias-слой нельзя удалять без миграционного периода, потому что Telegram хранит старые reply-клавиатуры на клиенте.

## 13. Профиль

Профиль показывает:

- RoleHub-имя;
- Telegram username;
- наличие аватара/фото;
- время последнего визита.

Редактирование:

```text
⚙️ Настройки героя
  -> 👤 Профиль героя
  -> ✍️ Имя героя
     -> следующее текстовое сообщение
     -> проверка длины, @, уникальности
  -> 🖼 Аватар героя
     -> следующее фото
     -> сохранить Telegram file_id
  -> 📖 История героя
     -> пока заглушка
```

Профиль спроектирован для расширения:

- простые дополнительные поля можно временно хранить в `profile_data`;
- поля с отдельными запросами, индексами и бизнес-логикой лучше выносить в отдельные таблицы;
- не превращать `profile_data` в неконтролируемый storage сложных сущностей.

## 14. Друзья

Текущий поток:

```text
🤝 Друзья и герои
  -> 🔎 Найти героя
  -> ввести RoleHub-имя или Telegram username
  -> найденная карточка
     -> 👤 Открыть профиль
     -> 🤝 Добавить в друзья
     -> 🌟 Искать ещё
```

Реализовано:

- поиск без учёта регистра;
- поиск сначала по `display_name`, затем по username;
- нельзя найти и добавить самого себя;
- создаётся заявка `Friendship(status="pending")`;
- дубликаты и обратные дубликаты запрещены.

Пока не реализовано:

- список друзей;
- список входящих заявок;
- принять или отклонить заявку;
- удалить друга;
- уведомление получателя о заявке.

## 17. Создание лобби

Актуальный поток:

```text
🌌 Войти в мир
  -> ✨ Создать свой мир
  -> 🌍 Открытый мир / 🔒 Тайный мир
  -> выбрать вселенную inline-кнопкой
  -> выбрать роль inline-кнопкой
     -> пагинация по 10 ролей
     -> поиск роли текстом
     -> случайная роль
  -> ввести max_players от 2 до 50
  -> проверить настройки
  -> 👑 Открыть мир
```

Правила:

- режим всегда `rp`;
- роль обязательна;
- размер от 2 до 50;
- размер не может превышать число уникальных ролей темы;
- пользователь не может состоять в двух лобби;
- новое лобби сейчас создаётся сразу со `status="active"`;
- срок активного лобби - 2 часа;
- owner сразу становится первым `LobbyMember`;
- код генерируется автоматически.

Важно: в старом архитектурном гайде могут встречаться устаревшие утверждения о фиксированных 15 участниках и waiting-статусе. Текущий код использует выбор 2-50 и создаёт active-лобби.

## 18. Темы и роли

Сейчас есть две вселенные:

- `brawl_stars` - Brawl Stars, 107 ролей;
- `mlp` - My Little Pony, 84 роли.

Файлы:

- `src/constants/topics.py`;

В БД хранится стабильный slug роли, пользователю показывается локализованное имя. В RP одна роль может принадлежать только одному joined-участнику конкретного лобби.

## 19. Поиск и вход в лобби

Текущий видимый поток:

```text
🌌 Войти в мир
  -> 🔎 Найти мир
  -> выбрать вселенную
  -> список active public лобби, 8 на страницу
  -> выбрать комнату inline-кнопкой
  -> выбрать свободную роль
  -> join_lobby()
```

Список показывает тему, заполнение и длительность лобби.

Особенность текущей реализации:

- экран выбора `по коду / по теме` существует;
- pending-action `enter_lobby_code` существует;
- обработчик кода существует;
- но видимая кнопка `🔎 Найти мир` сейчас ведёт сразу к выбору темы;
- поэтому вход по коду не достижим из актуальной пользовательской клавиатуры.

Если возвращать вход по коду, нужно восстановить видимый переход в `find_main` и покрыть его тестом.

## 20. Активное лобби

Текущие кнопки:

- `👥 Герои` - список участников и ролей;
- `📜 О мире` - информация о лобби;
- `🚪 Покинуть мир` - выход;
- `🌙 Закрыть мир` - только owner;
- `↩️ Назад`;
- `🏰 Главное меню`.

При выходе:

- membership получает `left`;
- `current_lobby_id` очищается;
- если ушёл owner, права переходят следующему joined-участнику;
- если участников не осталось, лобби закрывается.

Legacy waiting-flow остаётся в коде, но новые лобби создаются active. Кнопки `Обновить` и `Начать приключение` имеют handlers, однако текущая waiting-клавиатура их не показывает.

## 21. Сообщения внутри лобби

Если пользователь состоит в active-лобби и его сообщение не является кнопкой или pending-action:

1. сообщение преобразуется в `LobbyMessagePayload`;
2. сохраняется в БД;
3. отправляется всем другим joined-участникам;
4. отправителю обратно не дублируется;
5. ошибка доставки одному получателю не должна ломать отправку остальным.

В RP подпись сообщения - роль персонажа, а не Telegram username.

Важно соблюдать порядок обработки: поиск роли, ввод имени, фото профиля, поиск друга и другие pending-actions должны выполняться до обычной lobby-рассылки.

## 22. Очистка и срок жизни лобби

Фоновая задача запускается вместе с приложением и примерно раз в 60 секунд закрывает истёкшие лобби.

Текущий active TTL: 2 часа.

При закрытии лобби у joined-пользователей очищается `current_lobby_id`, участники получают системные уведомления.

## 25. База данных и миграции

Сейчас основной механизм схемы:

- `Base.metadata.create_all(engine)`;
- ручная функция `_ensure_runtime_columns()` для добавления некоторых колонок в старую SQLite БД;
- создание уникального индекса `users.display_name`.

Alembic-файлы присутствуют, но полноценный миграционный workflow фактически не используется.

Ограничения:

- runtime ALTER работает только для SQLite;
- сложные миграции данных этим способом делать нельзя;
- перед production и PostgreSQL нужно перейти на Alembic revisions;
- в моделях используется `datetime.utcnow()`, из-за чего тесты показывают deprecation warnings для Python 3.12+.

## 27. Известные ограничения и технический долг

Приоритетные проблемы:

1. Dev-доступ не является глобальным guard.
2. Вход по коду не достижим из видимой клавиатуры.
3. Friends поддерживает только создание pending-заявки.
4. `play_lobby.py` слишком большой и нуждается в постепенном разделении по сценариям.
5. Нет полноценных Alembic migrations.
6. Используются naive UTC timestamps и `datetime.utcnow()`.
7. README почти пустой.
8. Docker/Makefile scaffolding не является надёжным production-процессом.
9. Старый `BOT_ARCHITECTURE_GUIDE.md` местами содержит legacy-описания lobby-flow.
10. Некоторые скрытые support/FAQ функции остаются в коде, хотя не доступны из меню.

Функциональные заглушки:

- Premium и покупки;
- промокоды;
- оформление профиля;
- bio/описание профиля;
- язык;
- blacklist/privacy/reports;
- lobby/invite notification settings;
- принятие заявок в друзья.

## 28. Правила безопасного изменения проекта

Перед правкой:

1. проверить `git status`;
2. не удалять и не откатывать чужие незакоммиченные изменения;
3. изучить handler, keyboard, render и service одного сценария;
4. проверить, какие точные тексты используются в filters;
5. проверить pending-actions и очистку состояния.

При реализации:

1. держать Telegram routing в handlers;
2. бизнес-правила помещать в services;
3. запросы к БД помещать в repositories;
4. тексты экранов помещать в render, если это не короткая локальная ошибка;
5. кнопки и callback_data помещать в keyboards;
6. поддерживать childish-majestic стиль;
7. не ломать legacy button aliases;
8. коммитить только файлы проекта, не `.env`, вложения Codex и runtime-файлы.

После реализации:

1. запустить AST/import-проверку при крупных изменениях;
2. запустить `python -m pytest`;
3. проверить bot process после перезапуска;
4. обновить этот файл и `BOT_ARCHITECTURE_GUIDE.md`, если изменилась архитектура;
5. описать оставшиеся ограничения честно.

## 29. Критерии готовности новой функции

Функция считается завершённой, когда:

- есть понятный пользовательский путь;
- все кнопки ведут в ожидаемые экраны;
- `Назад` и `Главное меню` корректно очищают состояние;
- ошибки понятны пользователю;
- бизнес-правила не дублируются в handler;
- данные сохраняются через repository/service;
- добавлены тесты по риску изменения;
- весь текст соответствует стилистике;
- бот запускается без немедленного падения;
- документация отражает реальное поведение.
